# Модель данных и нормализация

Целевая реляционная модель PostgreSQL представлена в [ER PNG](er_diagram.png) и [PlantUML](er_diagram.puml). Реализованной БД и миграций в текущем проекте нет.

## Сущности и атрибуты

- **spaces**: id (PK), name, google_calendar_id — помещения и соответствующие календари.
- **users**: id (PK), platform, platform_user_id, fullname, role, space_id (FK) — учётная запись канала и привязка профиля к помещению.
- **bookings**: id (PK), user_id (FK), space_id (FK), start_time, end_time, description, status, reject_reason, calendar_event_id, created_at — заявки и результат согласования.
- **admin_logs**: id (PK), admin_id (FK), action, details, created_at — история действий администратора.

## Связи

Одно помещение имеет много заявок; у каждой заявки одно помещение. Один пользователь создаёт много заявок; каждая заявка принадлежит одному пользователю. Один администратор имеет много записей аудита; запись указывает одного администратора. Связь spaces–users задаёт помещение профиля. Для клиентов space_id может быть пустым; для назначения администратора — заполненным. На исходной диаграмме необязательность этой связи не выделена; это уточнение модели. Для назначения одного администратора нескольким помещениям понадобится отдельная таблица связей, она не включена в текущий вариант.

## Семантика и ограничения

Учётная запись идентифицируется парой (platform, platform_user_id), для которой требуется UNIQUE. Записи одного человека в Telegram и MAX считаются разными учётными записями, пока не введено связывание аккаунтов. ФИО не используется как ключ.

users.space_id — назначение/настройка профиля, bookings.space_id — фактически бронируемое помещение. Одно не вычисляется из другого: клиент может бронировать разные помещения. Идентификатор календаря хранится только в spaces, а имя пользователя не дублируется в bookings. Поле details — текст аудита, не альтернативное хранилище справочников.

Требуются FK для всех ссылок, CHECK(end_time > start_time), допустимые значения platform, role и status. Причина отказа обязательна для rejected; calendar_event_id — для подтверждённой брони после успешной синхронизации. Для времени следует использовать TIMESTAMPTZ; TIMESTAMP на исходной диаграмме — обобщённое обозначение. Запрет пересекающихся approved-интервалов одного помещения необходимо обеспечить атомарной проверкой и ограничением БД. Удаление учётной записи не должно уничтожать аудит.

## Проверка нормализации до 3НФ

**1НФ.** У каждой таблицы есть первичный ключ; значения скалярны, повторяющихся групп и списков ID в одном поле нет. fullname — одно отображаемое имя, система не требует работы с его частями.

**2НФ.** Неключевые атрибуты полностью зависят от ключа. Основные PK состоят из одного id, поэтому частичных зависимостей от части PK нет. В users альтернативный ключ (platform, platform_user_id) определяет одну запись целиком; один platform или один platform_user_id по отдельности пользователя не определяет.

**3НФ.** Для spaces: id → name, google_calendar_id; для users: id → platform, platform_user_id, fullname, role, space_id; для bookings: id → все атрибуты заявки; для admin_logs: id → admin_id, action, details, created_at. При указанных допущениях неключевые атрибуты не определяют другие неключевые атрибуты внутри своей таблицы. Сведения о пользователе, помещении и календаре вынесены в самостоятельные отношения, поэтому транзитивные зависимости через user_id и space_id не дублируют эти сведения в bookings.

Вывод: модель удовлетворяет 3НФ при зафиксированной семантике полей и уникальности учётной записи. Это логическое обоснование схемы, а не результат проверки реализованной БД.
