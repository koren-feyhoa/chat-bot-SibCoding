# Нефункциональные требования

Целевые критерии качества для проектируемой системы. Профили нагрузки и способы измерения уточнены как предложения для согласования командой; это не результаты испытаний. Из исходных материалов сохранены ориентиры 2 с, 1 с, 99%, 60 с и 70%.

| ID | Категория | Измеримый критерий | Проверка |
| --- | --- | --- | --- |
| NFR-01 | Производительность | Не менее 95% ответов на отправку заявки — до 2 с при 20 одновременных пользователях и нагрузке 5 запросов/с в течение 10 мин. | Нагрузочный тест; время измеряется от отправки клиентом до получения ответа, ошибки учитываются отдельно. |
| NFR-02 | Производительность | Не менее 95% ответов на /start — до 1 с при том же профиле нагрузки. | Метка отправки команды и получения ответа; измерения по обоим каналам. |
| NFR-03 | Доступность | Доступность пользовательских функций — не менее 99,0% за календарный месяц. | Проверка раз в минуту; доля успешных проверок. Плановый простой также учитывается. |
| NFR-04 | Надёжность | В тесте из 200 одновременно поданных уникальных заявок (100 Telegram и 100 MAX) не теряется ни одна принятая заявка. | Сверка подтверждённых номеров с БД: 100% сохранены, 0 дубликатов. При техническом отказе клиент не получает ложного подтверждения. |
| NFR-05 | Безопасность | 100% административных команд проходят серверную проверку роли; 0 успешных изменений от пользователя без соответствующей роли. | Негативные проверки для одобрения, отказа, отмены и управления справочниками. |
| NFR-06 | Безопасность | 100% соединений мессенджер–сервер используют HTTPS; целевая версия TLS — 1.3. | Проверка конфигурации конечных точек и согласуемого протокола; совместимость внешних API проверяется при внедрении. |
| NFR-07 | Аудит | 100% успешных административных действий фиксируются с ID администратора, действием, временем и деталями; роль приложения не может изменять или удалять записи аудита. | Сверка выполненных действий с журналом и отрицательные проверки UPDATE/DELETE от роли приложения. |
| NFR-08 | Масштабируемость | Добавление помещения или администратора: 0 изменений исходного кода, 0 перезапусков процессов; запись доступна следующему запросу после сохранения. | Добавление через предусмотренную административную функцию и повторное чтение справочника. |
| NFR-09 | Масштабируемость | Для каждого адаптера допускаются 2 одновременно работающих экземпляра; при суммарных 10 запросах/с за 10 мин — 0 потерь и дубликатов принятых заявок. | Нагрузочный тест двух экземпляров; согласованная доставка обновлений одного бота обязательна. |
| NFR-10 | Удобство | Путь создания заявки после /start содержит не более 4 переходов: помещение, дата/время, описание, подтверждение. | Проверка одинаковой последовательности в Telegram и MAX; нажатия клавиш при вводе текста не считаются переходами. |
| NFR-11 | Удобство | 100% уведомлений о решении передаются клиенту не позднее 60 с после сохранения статуса при доступном API мессенджера. | Сравнение времени изменения статуса и успешной отправки уведомления; сбои API фиксируются отдельно. |
| NFR-12 | Сопровождаемость | Выделены 3 логических модуля: ядро, Telegram-адаптер, MAX-адаптер; 0 прямых импортов одного адаптера другим. | Проверка структуры и зависимостей модулей; общие правила находятся в ядре. |
| NFR-13 | Тестируемость | Покрытие строк модулей критической логики создания заявки и проверки пересечений unit-тестами — не менее 70%. | Отчёт покрытия с явно заданным составом критических модулей. |

Для тестов времени ответа используется стабильное соединение; окружение, версии и доступность внешних API фиксируются в протоколе. Цель 99,0% задаётся процентом, без противоречивого фиксированного предела 7 часов: допустимое время простоя зависит от длины месяца. TLS 1.3 — целевое условие, совместимость должна быть подтверждена. Горизонтальное масштабирование адаптеров требует механизма распределения обновлений и защиты от повторов; простого запуска двух независимых polling-процессов недостаточно.
