# Функциональные требования

Требования к целевой ИС бронирования. Основание — [процесс To-Be](../bpmn/to_be_description.md) и [диаграмма вариантов использования](use_cases.png).

| ID | Требование | Связь с процессом |
| --- | --- | --- |
| FR-01 | Идентифицировать клиента и администратора по платформе и ID, проверять роль перед предоставлением административных функций. | Вход в процесс; A1, A6 |
| FR-02 | Показывать клиенту список доступных коворкингов и позволять выбрать помещение. | Выбор помещения; A2 |
| FR-03 | Показывать занятые интервалы выбранного помещения на выбранную дату. | Проверка календаря; A2 |
| FR-04 | Принимать заявку с ФИО, помещением, датой, временем и описанием; проверять обязательные поля, начало раньше конца и доступность слота, сохранять свободную заявку как pending. | Ввод и сохранение; A2, A3 |
| FR-05 | Уведомлять клиента об одобрении, отклонении или отмене заявки в мессенджере, из которого она поступила. | Завершение процесса; A4 |
| FR-06 | Уведомлять администратора о новых заявках и показывать их данные для рассмотрения. | Передача на согласование; A4 |
| FR-07 | Позволять администратору одобрить заявку после повторной проверки доступности; создавать событие Google Calendar и сохранять его ID и статус approved. | Ветка одобрения; A2, A3, A5 |
| FR-08 | Позволять администратору отклонить заявку с указанием причины, сохранять rejected и передавать причину клиенту. | Ветка отказа; A3, A4 |
| FR-09 | Позволять администратору отменить одобренную бронь, удалить связанное событие календаря, сохранить cancelled и уведомить клиента. | Исключение после одобрения; A3–A5 |
| FR-10 | Позволять уполномоченному администратору управлять помещениями, связями с календарями и назначениями администраторов; журналировать административные изменения. | Сопровождение процесса; A6 |

Критерии приёмки: некорректный или занятый интервал не становится одобренной бронью; пользователь без роли не выполняет административную команду; одобренная бронь имеет событие календаря; отказ сохраняет причину; отменённое событие удаляется; клиент получает результат в исходном канале. Требования описывают To-Be и не подтверждают внедрение всех функций.
