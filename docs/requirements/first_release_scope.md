# Границы первой версии СибКодинг

Задача: [#14](https://github.com/koren-feyhoa/chat-bot-SibCoding/issues/14). Ответственная: Карина Кузнецова.

Статус: предложение для согласования через Pull Request. Подтверждение команды ещё не получено. Версия планируемого функционального релиза — 0.1.0; выпуск тега и релиза выполняется отдельно после приёмки реализации. Этот документ не подтверждает готовность текущего кода.

## Цель и пользователи

Первая версия позволяет студенту или сотруднику подать заявку на бронирование одного пространства «СибКодинг» через Telegram, а администратору — согласовать, отклонить или отменить бронь. Занятость и подтверждённые события связаны с одним Google Calendar. Главная цель — завершённый и проверенный сценарий без конфликтующих подтверждённых броней.

Предлагается сначала стабилизировать существующий Telegram-сценарий: в текущем коде он уже есть, тогда как MAX реализован частично. Ограничение одним помещением сокращает объём первого выпуска и позволяет проверить согласование и интеграцию календаря до добавления второго канала и справочников.

## Соответствие функциональным требованиям

Полные целевые требования сохраняются в [functional.md](functional.md). Ограничения ниже относятся только к первому релизу и не отменяют целевой объём.

| Требование | Объём версии 0.1.0 | Последующие версии |
| --- | --- | --- |
| FR-01 Идентификация и роли | Идентификация по Telegram ID; проверка роли для всех административных действий | Идентификация MAX и единая модель платформенных учётных записей |
| FR-02 Выбор помещения | Единственное помещение явно показано пользователю и выбрано автоматически; полный выбор из справочника отложен | Список нескольких помещений и выбор пользователем |
| FR-03 Занятые интервалы | Просмотр занятости единственного помещения на выбранную дату | Занятость отдельно для каждого помещения |
| FR-04 Создание заявки | ФИО, дата, начало, конец, цель; проверка полей и интервала; сохранение pending | Тот же сценарий для MAX и нескольких помещений |
| FR-05 Уведомления клиента | Одобрение, отклонение с причиной и отмена через Telegram | Доставка в MAX по исходному каналу |
| FR-06 Уведомления администратора | Новая заявка и данные для рассмотрения через Telegram | Распределение заявок по администраторам помещений |
| FR-07 Одобрение | Повторная проверка занятости, защита от повторов и конкурирующих решений, событие календаря, approved и ID события | Расширение на несколько помещений и оба канала |
| FR-08 Отклонение | Обязательная причина, rejected и уведомление клиента | Общий сценарий обоих каналов |
| FR-09 Отмена | Администратор отменяет одобренную бронь; событие удаляется, cancelled и история сохраняются, клиент уведомляется | Расширение на несколько помещений |
| FR-10 Управление справочниками | Интерфейс управления помещениями, календарями и назначениями не входит; административные решения журналируются | Управление справочниками и назначениями без изменения кода и перезапуска |

## Обязательные свойства первого релиза

- Полномочия проверяются при выполнении операции, включая команды и callback; принадлежность к чату сама по себе не должна давать неоговорённых прав.
- Даты и отображение используют Asia/Krasnoyarsk; начало раньше окончания, прошедшие интервалы не принимаются. Остальные ограничения уточняются в [#15](https://github.com/koren-feyhoa/chat-bot-SibCoding/issues/15).
- Нельзя подтвердить две пересекающиеся брони одного помещения. Повторное нажатие не создаёт ещё одно событие.
- Успешно принятые заявки и статусы переживают перезапуск. Ошибка сохранения не выдаётся за успех.
- Ошибка или неизвестный результат Google Calendar не превращаются в ложное подтверждение. Повтор операции не создаёт дубль.
- Сбой доставки уведомления различается со сбоем бронирования; недоставленное сообщение можно обнаружить и повторить.
- Интерфейс позволяет выйти из ввода в меню и начать заново без старых данных.
- В репозитории и отчётах отсутствуют действующие секреты и реальные данные заявок.

## Что отложено

1. Полноценный MAX-адаптер и одновременное обслуживание двух мессенджеров — после приёмки Telegram-сценария.
2. Несколько помещений, выбор календаря по справочнику и назначения администраторов по помещениям — следующий функциональный этап.
3. Изменение справочников через административный интерфейс без перезапуска — вместе с поддержкой нескольких помещений.
4. Горизонтальное масштабирование адаптеров — после выбора транспорта и реализации общего ядра.

Общее ядро FastAPI и PostgreSQL остаются целевым направлением [ADR-001](../adr/001_architecture_style.md), который пока предложен. Их архитектура и этап внедрения согласуются в [#20](https://github.com/koren-feyhoa/chat-bot-SibCoding/issues/20); задача #14 не утверждает ADR вместо команды. Первый выпуск в любом случае обязан выполнить требования сохранности и отсутствия конфликтов; одно лишь сохранение текущего JSON не считается доказательством надёжности.

Самостоятельная отмена клиентом, автоматическое одобрение, напоминания, веб-панель, связывание аккаунтов Telegram/MAX и проверка принадлежности к СФУ не добавляются автоматически. При необходимости для них согласуются отдельные требования и задачи.

## Качество и приёмка

[NFR-01–NFR-13](non_functional.md) остаются целевыми требованиями. Для первого выпуска обязательны проверки прав, сохранности, аудита, повторных операций, ошибок календаря и корректности диалога. Условия измерения задержек, четырёх шагов и покрытия фиксируются в [#17](https://github.com/koren-feyhoa/chat-bot-SibCoding/issues/17), тест-план — в [#55](https://github.com/koren-feyhoa/chat-bot-SibCoding/issues/55).

Требования двух каналов, нескольких экземпляров и управления справочниками проверяются на соответствующих следующих этапах. Это предлагаемое изменение очередности, которое команда должна подтвердить, а не заявление о выполнении всех NFR. Доступность 99% за месяц нельзя подтвердить разовой демонстрацией: нужен мониторинг за период. До согласования правил и методов проверки релиз не объявляется готовым.

## Демонстрационный сценарий

Использовать отдельный тестовый бот, тестовый календарь и вымышленные данные.

1. Клиент открывает /start, видит помещение «СибКодинг» и занятость выбранной даты.
2. Вводит корректные данные для свободного будущего интервала. Получает номер и статус pending; администратор получает заявку.
3. Пользователь без роли пытается выполнить административное действие — получает отказ.
4. Администратор одобряет заявку. В календаре ровно одно событие, сохранены approved и ID; клиент получает подтверждение. Повторный клик не создаёт дубль.
5. Второй клиент пытается забронировать пересекающийся интервал — подтверждённая конфликтующая бронь не возникает. Отдельно проверяются две заявки, созданные до одобрения первой.
6. Для другой заявки администратор вводит причину отказа: сохраняется rejected, причина приходит клиенту, события в календаре нет.
7. Администратор отменяет одобренную будущую бронь: событие удалено, cancelled и история сохранены, клиент уведомлён.
8. После перезапуска записи и статусы сохранены. При имитации сбоя календаря система не сообщает ложный успех; результат можно восстановить без дубля.

Проверяющая — Елена; техническое подтверждение — Натан; решение о выпуске — Карина. К демонстрации прикладывается протокол фактических результатов, а не только этот сценарий.
